## Step 1: Flyway V10 Database Foundation

### 1. Executive Summary & Objectives
Phase 7.3.2 evolves ShieldOps from a live-tested API security research platform into an operationally resilient, evidence-driven Security Operations Center (SOC). 

Step 1 establishes the durable database foundation required for:
1. **API Event Attribution**: Providing granular attribution (`simulation_run_id`, `simulation_campaign_id`, `simulation_scenario_id`, `simulation_stage`, `tenant_id`, `service_name`) to every telemetry event without fabricating synthetic tenant defaults.
2. **Durable Simulation Runs**: Persisting campaign orchestrations and stage executions across process restarts, node crashes, and container redeployments.
3. **Optimistic Locking & Lifecycle Enforcement**: Guaranteeing state machine integrity (`PENDING`, `RUNNING`, `PAUSED`, `STOPPED`, `COMPLETED`, `INTERRUPTED`, `FAILED`) and execution provenance.
4. **Zero Destructive Data Modification**: Preserving all historical events, evidence, incidents, campaigns, and advisory policy decisions.

#### 2.2 `security_data.simulation_runs` Table
Persists orchestration metadata and runtime metrics:
```sql
CREATE TABLE IF NOT EXISTS security_data.simulation_runs (
    run_id VARCHAR(64) PRIMARY KEY,
    campaign_id VARCHAR(64),
    template_id VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL DEFAULT 'PENDING',
    requested_by VARCHAR(128),
    start_time TIMESTAMP WITH TIME ZONE NOT NULL,
    end_time TIMESTAMP WITH TIME ZONE,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    last_heartbeat_at TIMESTAMP WITH TIME ZONE,
    duration_seconds INT NOT NULL DEFAULT 60,
    request_rate DOUBLE PRECISION NOT NULL DEFAULT 10.0,
    concurrency INT NOT NULL DEFAULT 1,
    traffic_mix VARCHAR(32) NOT NULL DEFAULT 'SEQUENTIAL',
    dry_run BOOLEAN NOT NULL DEFAULT FALSE,
    deterministic_seed BIGINT,
    total_requests INT NOT NULL DEFAULT 0,
    requests_2xx INT NOT NULL DEFAULT 0,
    requests_4xx INT NOT NULL DEFAULT 0,
    requests_5xx INT NOT NULL DEFAULT 0,
    all_passed BOOLEAN NOT NULL DEFAULT FALSE,
    provenance_json TEXT,
    failure_reason TEXT,
    stop_reason TEXT,
    version BIGINT NOT NULL DEFAULT 0,
    CONSTRAINT chk_sim_runs_status CHECK (status IN ('PENDING', 'RUNNING', 'PAUSED', 'STOPPED', 'COMPLETED', 'INTERRUPTED', 'FAILED'))
);
```

#### 2.3 `security_data.simulation_run_stages` Table
Persists granular stage execution progress and assertions:
```sql
CREATE TABLE IF NOT EXISTS security_data.simulation_run_stages (
    id UUID PRIMARY KEY,
    run_id VARCHAR(64) NOT NULL REFERENCES security_data.simulation_runs(run_id) ON DELETE CASCADE,
    stage_id VARCHAR(64) NOT NULL,
    stage_name VARCHAR(128) NOT NULL,
    scenario_id VARCHAR(64) NOT NULL,
    status VARCHAR(32) NOT NULL,
    total_requests INT NOT NULL DEFAULT 0,
    success_requests INT NOT NULL DEFAULT 0,
    failed_requests INT NOT NULL DEFAULT 0,
    assertions_json TEXT,
    executed_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT uq_sim_stage_run_scenario UNIQUE (run_id, stage_id, scenario_id)
);
```

### 3. Index Rationale & Query Optimizations
1. `idx_api_events_sim_run_id`: Fast filtering of telemetry generated by a simulation run.
2. `idx_api_events_tenant_id`: Rapid scoping of multi-tenant SOC investigation queries.
3. `idx_api_events_ip_timestamp`: Optimizes Network Intelligence queries (`source_ip, timestamp DESC`) to identify top suspicious IP addresses over rolling time windows.
4. `idx_sim_runs_status`: Efficient polling of active/running simulations (`RUNNING`, `PAUSED`) for heartbeat monitoring and crash recovery.
5. `idx_sim_runs_template`: Fast historical run queries filtered by campaign template.
6. `idx_sim_runs_start_time`: Time-series sorting of simulation run history (`start_time DESC`).
7. `idx_sim_stages_run_id`: Fast joining and stage retrieval for a specific simulation run.
8. `idx_sim_stages_scenario_id`: Aggregation of scenario pass/fail benchmarks across runs.

## Step 2: Persistent Simulation Runtime Orchestration and Recovery Engine

### 1. Step 2 Objectives
Step 2 transforms the in-memory simulation engine into a durable, crash-resilient runtime service:
1. **Durable Persistence Service**: Implement `SimulationRunRepository` using standard, dialect-agnostic SQL that functions identically on PostgreSQL and H2 in-memory test databases.
2. **Crash Recovery Reconciliation**: Automatically reconcile uncompleted runs (`RUNNING`, `PAUSED`) whose heartbeat is stale upon gateway restart, safely marking them as `INTERRUPTED`.
3. **Heartbeat & Optimistic Locking**: Maintain live heartbeat timestamps during testbed executions and increment version counters for concurrency control.
4. **End-to-End Telemetry Attribution**: Propagate simulation attribution headers (`X-Simulation-Run-Id`, `X-Simulation-Campaign-Id`, `X-Simulation-Scenario-Id`, `X-Simulation-Stage`, `X-Simulation-Tenant`, `X-Tenant-Id`, `X-Service-Name`) from HTTP requests through `TelemetryFilter`, into Redis Streams, and persist into PostgreSQL via `TelemetryDrainWorker`.
5. **Multi-Source Hybrid Querying**: Expose unified run query mechanisms in `SimulationExecutionService` combining live in-memory execution contexts with durable PostgreSQL database records.

---

### 2. Architecture & Components

#### 2.1 `SimulationRunRepository`
Located at `gateway/src/main/java/com/aegis/gateway/simulation/repository/SimulationRunRepository.java`.
- `saveRun(SimulationRunResponse run)`: Checks existence via `SELECT COUNT(*)`, executing targeted `UPDATE` or `INSERT` to guarantee portability across PostgreSQL and H2.
- `saveStage(String runId, SimulationStageResult stage)`: Persists granular stage executions and serializes assertions to JSON.
- `updateHeartbeat(String runId)`: Updates `last_heartbeat_at = CURRENT_TIMESTAMP`, `updated_at = CURRENT_TIMESTAMP`.
- `updateRunStatus(String runId, SimulationRunStatus status, String stopReason, String failureReason)`: Handles lifecycle transitions (`PAUSED`, `RUNNING`, `STOPPED`, `COMPLETED`, `FAILED`, `INTERRUPTED`).
- `findRunById(String runId)`: Queries run record and populates associated execution stages.
- `findAllRuns(int limit, int offset)`: Retrieves paginated historical runs ordered by `start_time DESC`.
- `reconcileInterruptedRuns(Instant heartbeatCutoff)`: Identifies orphan `RUNNING` or `PAUSED` simulations whose last heartbeat exceeds the cutoff and transitions them to `INTERRUPTED` with `stop_reason = 'Gateway restart / ungraceful termination detected'`.

#### 2.2 `SimulationExecutionService` Integration
- **`@PostConstruct initCrashRecovery()`**: Automatically triggers `reconcileInterruptedRuns(Instant.now().minusSeconds(120))` when the Spring ApplicationContext starts up.
- **Run Lifecycle Persistence**: Persists initial run on `startRun()`, updates status on `pauseRun()`, `resumeRun()`, and `stopRun()`.
- **Progress Tracking**: Records stage completion and updates heartbeat after each stage in `executeRun()`.
- **Hybrid Querying**: In `getRun(runId)`, checks active in-memory map first, then queries `SimulationRunRepository`. In `listRuns()`, merges database historical runs with active memory contexts, deduplicating by `runId`.

#### 2.3 Telemetry Attribution Pipeline
1. `SimulationExecutionService`: Attaches `X-Simulation-Run-Id`, `X-Simulation-Campaign-Id`, `X-Simulation-Scenario-Id`, `X-Simulation-Stage`, `X-Simulation-Tenant`, `X-Tenant-Id`, and `X-Correlation-Id` to all simulated HTTP requests.
2. `TelemetryFilter`: Extracts attribution headers and derives `serviceName` from the request path (`customer-service`, `account-service`, `transaction-service`, `gateway`).
3. `Redis Streams`: Includes all 6 attribution fields in `publishToRedisOrDatabase`.
4. `TelemetryDrainWorker` & `DetectionStreamConsumer`: Reads all 29 fields including attribution metadata, preserving `tenant_id = null` for requests without tenant context.

## Step 3: Network & Identity Intelligence and Infrastructure Observability Backend APIs

### 1. Step 3 Objectives
Step 3 equips ShieldOps with operational security intelligence APIs and live infrastructure metrics:
1. **Network Intelligence API (`/api/v1/soc/network-intelligence`)**: Aggregate observed client IPs, error ratios (4xx/5xx), sensitive route probes, and local reputation classification ("LOCAL_LOOPBACK", "INTERNAL_NETWORK", "OBSERVED_EXTERNAL") without fabricated third-party threat scores.
2. **Identity Intelligence API (`/api/v1/soc/identity-intelligence`)**: Aggregate observed authentication subjects, customer IDs, roles, request volumes, error ratios, and risk categorization ("HIGH_RISK", "ELEVATED", "BENIGN").
3. **Tenant Activity API (`/api/v1/soc/tenant-activity`)**: Monitor multi-tenant partition metrics, activity windows, and error rates across observed tenants.
4. **Infrastructure Observability API (`/api/v1/soc/infrastructure-observability`)**: Provide genuine, non-fabricated system observability:
   - Real JVM Heap (used, max, committed, free) and Thread counts (active, peak, daemon) via `java.lang.management.ManagementFactory`.
   - Real PostgreSQL connection pool telemetry via `HikariPoolMXBean` (active, idle, total, max connections) and connectivity health probe (`SELECT 1`).
   - Real Redis Stream status and stream length (`xlen`) via `StringRedisTemplate`.
   - Telemetry processing throughput, hourly rates, and data freshness metrics.
5. **Correlation Navigation & Attribution Filters**:
   - `GET /api/v1/security/events/correlation/{correlationId}`: Retrieve full request trace in chronological order.
   - Filter support for `simulationRunId` and `tenantId` in `GET /api/v1/security/events`.

---

### 2. Endpoints & Data Model Deliverables

#### 2.1 Network Intelligence
- Endpoint: `GET /api/v1/soc/network-intelligence?windowHours=24&limit=50`
- Response: `NetworkIntelligenceResponse` containing `List<ObservedIpRecord>`:
  - `ipAddress`: Client IP.
  - `firstSeen` & `lastSeen`: Timestamps.
  - `totalRequests`, `requests2xx`, `requests4xx`, `requests5xx`, `errorRate`.
  - `uniqueEndpointsCount`, `suspiciousActivityCount`, `tenantCount`, `identityCount`.
  - `reputationStatus`: Derived locally ("LOCAL_LOOPBACK", "INTERNAL_NETWORK", "OBSERVED_EXTERNAL").
  - `reputationSource`: "LOCAL_EVALUATION".

#### 2.2 Identity Intelligence
- Endpoint: `GET /api/v1/soc/identity-intelligence?windowHours=24&limit=50`
- Response: `IdentityIntelligenceResponse` containing `List<ObservedIdentityRecord>`:
  - `subject`: Authentication subject/UUID.
  - `customerId`, `roles`.
  - `totalRequests`, `requests2xx`, `requests4xx`, `requests5xx`.
  - `uniqueIpsCount`, `tenantCount`, `anomalousEventsCount`.
  - `riskCategory`: "HIGH_RISK" (suspicious > 5 or errorRate > 50%), "ELEVATED" (suspicious > 0 or errorRate > 20%), or "BENIGN".

#### 2.3 Tenant Activity
- Endpoint: `GET /api/v1/soc/tenant-activity?windowHours=24&limit=50`
- Response: `TenantActivityResponse` containing `List<TenantActivityRecord>`:
  - `tenantId`: Tenant identifier.
  - `totalRequests`, `requests2xx`, `requests4xx`, `requests5xx`, `errorRate`.
  - `uniqueIdentitiesCount`, `uniqueIpsCount`.
  - `firstSeen` & `lastSeen`.

#### 2.4 Infrastructure Observability
- Endpoint: `GET /api/v1/soc/infrastructure-observability`
- Response: `InfrastructureObservabilityResponse`:
  - `gatewayStatus`: "HEALTHY" / "DEGRADED".
  - `uptimeSeconds`: JVM uptime.
  - `jvm`: Heap memory (used/max/committed) and active/peak threads.
  - `database`: Status ("CONNECTED"), active, idle, total, max connections from HikariCP.
  - `redis`: Status ("CONNECTED"), stream key, current stream length, ping response.
  - `telemetryPipeline`: Total events persisted, events in the last hour, latest event timestamp, data freshness in seconds, failure counter.

#### 2.5 Correlation Navigation & Event Filtering
- `GET /api/v1/security/events/correlation/{correlationId}`: Returns all events linked by a correlation ID ordered by `timestamp ASC`.
- `GET /api/v1/security/events`: Extended with `simulationRunId` and `tenantId` parameters.
